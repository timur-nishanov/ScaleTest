# Аналитика — схема логирования

По ТЗ («Технические особенности») и переписке в комментариях: **единая таблица**, одна строка = одна попытка; админ-панель не нужна — достаточно выгрузки Excel/CSV.

## Строка попытки (`AttemptRow`, src/analytics/events.ts)

| Колонка | Тип | Назначение |
|---|---|---|
| `session_id` | TEXT (UUID) | генерируется по тапу «Начать», группирует попытки одного игрока |
| `visit_seq` | INTEGER | сквозной счётчик визитов на киоске (вторичный ключ склейки со сканером лидов) |
| `session_start_ts` | TEXT ISO 8601 +TZ, мс | якорь склейки со сканером — момент старта визита |
| `event_ts` | TEXT ISO 8601 +TZ, мс | метка попытки/ответа |
| `mode` | TEXT | `build` / `ready` |
| `task_id` | TEXT | id задачи (`logs`, `etl`, `rt`, …) |
| `task_title` | TEXT | название задачи |
| `outcome` | TEXT | `correct` / `partial` / `wrong` / `timeout` |
| `earned_coin` | INTEGER 0/1 | начислена ли монета |
| `duration_sec` | INTEGER | от входа в задачу до ответа |
| `bundle_choice` | TEXT | выбранный бандл (только ready) |
| `viewed_bundles` | TEXT | открытые бандлы, напр. `Бандл A,Бандл C` (см. примечание) |
| `ans_<svc>` ×13 | INTEGER 0/1 | сервис вошёл в подтверждённый ответ |
| `tap_<svc>` ×13 | INTEGER | сколько раз сервис «рассматривали» (интерес) |

Ключи сервисов: `pg, mysql, ch, valkey, storedoc, kafka, greenplum, opensearch, airflow, spark, ytsaurus, ydb, datalens` (совпадают с данными и именами файлов ассетов).

**Примечания к семантике:**
- Ветка A: «неверно» пишется как `wrong` (в UI заголовок «Почти!»); `partial` используется только в ready (рабочий, но не лучший бандл).
- `timeout` в ready по ТЗ даёт монету (`earned_coin=1`), в build — нет.
- `viewed_bundles`: в актуальном макете описания всех бандлов видны сразу (нет пошагового открытия), поэтому поле заполняется всеми бандлами задачи. Если вернём панель с открытием по тапу — начнёт отражать реальные открытия. Колонку сохраняем для совместимости с таблицей ТЗ.
- Отдельные тап-события в реальном времени не шлём — счётчики тапов агрегируются в строке попытки (покрывает задачу «интерес к сервисам»). Если пост-анализу нужны сырые тапы с таймстемпами — добавим второй поток событий, транспорт готов.

## Транспорт (src/analytics/sink.ts)

1. Строка попытки кладётся в очередь `localStorage` (переживает перезагрузку киоска, работает без сети).
2. При заданном `VITE_ANALYTICS_URL` очередь отправляется POST-батчами (`{attempts: [...]}`) с повтором при офлайне.
3. Этап 4 плана: приёмник + хранилище (SQLite/Postgres) + выгрузка `.xlsx`. Формат выгрузки — ровно таблица выше, один лист.

Отладка на стенде: `dumpQueue()` в консоли возвращает накопленную очередь.
